# V5 数据关系与库存并发

1. **本阶段目标**：让表之间的关系可见，并让库存扣减在并发下不超卖。
2. **上一阶段有什么**：V4 的事务让单个订单的多次写入一起提交，但先读库存再扣减仍会竞争。
3. **本阶段新增什么**：分类表、外键、订单明细 JOIN、索引和条件 UPDATE。
4. **纵向请求链**：Controller → OrderService → 读取商品 → 写订单/明细 → `UPDATE product SET stock=stock-? WHERE id=? AND stock>=?` → 检查受影响行数。
5. **数据形态变化**：分类 ID 关联商品；订单快照与当前分类通过 JOIN 组成 `OrderLineVO`。
6. **新增技术的位置**：外键在数据库约束关系；索引帮助过滤与 JOIN；行锁使条件扣减在同一行上串行化。
7. **核心目录变化**：`Category`、`CategoryMapper`、`OrderLineVO`、`database/migrations/v5.sql`。
8. **API 变化**：`GET /api/categories`；商品可以写入和查询 `categoryId`；订单详情多了分类名称。
9. **数据库变化**：新增 category；product.category_id 和 order_item.order_id 外键；商品状态/价格等索引。历史订单保留商品快照，因此 order_item.product_id 只建索引，商品删除后仍能读取历史订单。
10. **手工验证步骤**：执行 V5 迁移；创建仅剩 1 件库存的商品，同时发两个数量为 1 的下单请求，应恰好一个成功，另一个 409；库存为 0。运行迁移中的两个 EXPLAIN，观察 `key`、`rows` 和 `Extra`；优化器对小表可能仍选主键。
11. **自动测试**：`mvn test && mvn package`；`npm ci && npm run build`。
12. **常见错误**：只在 Java 中判断库存；忽略 UPDATE 的 affected rows；给低选择性的字段盲目建索引；多商品订单按不固定顺序扣库存。
13. **本阶段掌握判定**：能解释原子性属于事务，隔离级别和 MVCC 影响并发可见性；InnoDB 对同一行更新加行锁。本实现使用条件 UPDATE，未使用乐观锁版本号或 `SELECT FOR UPDATE` 悲观锁。
14. **下一阶段为什么存在**：商品详情的重复读取仍直达 MySQL，V6 加入缓存支线。
15. **checkout 当前版本**：`git checkout v5`。
