# V6 Redis 缓存支线

1. **本阶段目标**：让重复的商品详情读取先走缓存。
2. **上一阶段有什么**：数据库关系、索引和原子库存扣减，商品详情每次仍直达 MySQL。
3. **本阶段新增什么**：Redis Cache Aside、TTL、空值短缓存、更新失效与日志。
4. **纵向请求链**：Controller → ProductService → Redis；命中直接返回，未命中查 MySQL 并写 Redis。Redis 故障时退回 MySQL。
5. **数据形态变化**：Product ↔ JSON 字符串 ↔ Redis key `minimall:product:{id}`。
6. **新增技术的位置**：`ProductCache` 位于 Service 和 Mapper 之间，不替换数据库作为真实数据源。
7. **核心目录变化**：新增 `cache/ProductCache.java`、`ProductCacheTest` 和 Redis 环境配置。
8. **API 变化**：无，`GET /api/products/{id}` 契约保持不变。
9. **数据库变化**：无。
10. **手工验证步骤**：启动 Redis、MySQL 和后端；连续请求同一商品两次，日志先出现 `CACHE MISS`、`DB QUERY`，第二次出现 `CACHE HIT`；修改商品后看到 `CACHE EVICT`，再读应未命中。下单扣库存提交后也应失效。重复查不存在的 ID，第二次命中 20 秒空值缓存。
11. **自动测试**：`mvn test && mvn package` 中的 ProductCacheTest 验证命中、未命中、空值 TTL 和 Redis 故障退回；前端 `npm ci && npm run build`。
12. **常见错误**：更新数据库却不删缓存；在事务提交前删缓存导致旧数据回填；把库存长期缓存；Redis 故障导致主链不可用。
13. **本阶段掌握判定**：缓存穿透是大量不存在的 key，本阶段用短期空值保护；缓存击穿是热点 key 同时失效，缓存雪崩是大量 key 同时失效，本阶段只介绍风险，不声称解决。
14. **下一阶段为什么存在**：订单成功后的通知仍在同步链，V7 用 MQ 分离异步工作。
15. **checkout 当前版本**：`git checkout v6`。
