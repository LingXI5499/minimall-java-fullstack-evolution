# V7 RabbitMQ 异步消息

1. **本阶段目标**：把订单成功后的模拟通知从同步 HTTP 请求链中拆出去。
2. **上一阶段有什么**：订单事务、Redis 缓存失效；通知尚未异步处理。
3. **本阶段新增什么**：`OrderCreatedEvent`、RabbitMQ 生产者/消费者、交换机、队列、绑定、重试与死信队列。
4. **纵向请求链**：Controller → OrderService 提交订单 → `AFTER_COMMIT` 监听器 → Producer → Exchange → Binding → Queue → Consumer → `order_notification`。
5. **数据形态变化**：Java 事件 → JSON 消息 → Java 事件 → 数据库模拟通知记录。
6. **新增技术的位置**：RabbitMQ 是提交后的异步支线，不参与 MySQL 事务。
7. **核心目录变化**：新增 `messaging`、通知 Mapper/XML 和 `database/migrations/v7.sql`。
8. **API 变化**：无；订单创建响应不等待消费者写通知。
9. **数据库变化**：`order_notification.order_id` 唯一，重复投递只生成一条记录。
10. **手工验证步骤**：启动 MySQL、Redis、RabbitMQ；执行 V7 迁移；创建订单，查看生产者/消费者日志并用 SQL 查通知记录。发送相同消息两次，第二次应被唯一键去重。用 V4 回滚开关验证回滚后无消息。
11. **自动测试**：`mvn test && mvn package`；`npm ci && npm run build`。
12. **常见错误**：事务尚未提交就发消息；消费异常仍 ACK；重复投递重复执行；RabbitMQ 故障时误以为本阶段具备可靠投递。
13. **本阶段掌握判定**：能解释 Exchange 按 routing key 分发到 Queue，Consumer 成功处理后 ACK；失败重试 3 次后拒绝重入队并进入死信队列。去重只保证本项目的模拟通知不会重复写入；提交后 broker 不可用仍可能丢消息，生产方案可用事务 Outbox。
14. **下一阶段为什么存在**：消息处理在后台发生，浏览器还不能实时得知，V8 加入 WebSocket 与时间入口。
15. **checkout 当前版本**：`git checkout v7`。
